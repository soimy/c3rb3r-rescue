# 找不到可用密钥时的 Btrfs 恢复

[English](btrfs-recovery.md) | 简体中文

先保全仍可取得的内存。这条路线从文件系统中重组更早的字节，不是破解加密。依据为 [crt106 的社区实现](https://github.com/crt106/c3rb3r-btrfs-recovery/tree/b831f3a0f718677b889f2998ff09a0b925baa56b)和[用户报告](https://github.com/soimy/c3rb3r-rescue/issues/12)，维护者没有在本轮执行实盘恢复验收。

## 为什么旧数据可能还在

Btrfs 写时复制可能为覆盖写分配新空间。文件未改写的部分仍可能引用一个更大的旧 extent，使其中部分加密前字节继续可读，常称为 bookend extent。恢复必须证明这些字节对应原文件的哪些位置；物理地址相邻本身不够。

| 条件 | 应如何理解 |
|---|---|
| 有完好快照或独立原件 | 先验证并从中复制，保留快照，无需猜测旧块。 |
| 部分加密，仍有旧 extent 引用 | 映射和边界检查后可尝试重组；仅有部分加密模式不构成证明。 |
| 有 NoCOW 标志或关闭了校验和 | 不要直接放弃。曾被快照／其他引用共享的 extent 可能必须 CoW。`last_snapshot` 是线索，不是逐文件证明；不同配置中 `nodatasum` 与 NoCOW 不能直接画等号。 |
| 整个旧 extent 已替换且失去所有引用 | 可能已释放、复用或 discard；当前引用未必能恢复，旧树根／快照或专业雕刻需另行评估。 |
| 压缩、inline、重复加密或不支持的条带布局 | 需要适配实现并单独验证，不能强套线性 extent 公式。 |
| ext4 或 ZFS | 此 Btrfs 工具不适用，保留证据并使用对应文件系统的流程。 |

`0x24` 往往比 `0x25`／`0x26` 更少留下引用，但仅凭尺寸或模式都不能证明可恢复或永久丢失。上游原理参考 [Btrfs 功能](https://btrfs.readthedocs.io/en/latest/Introduction.html)和 [btrfs(5)](https://btrfs.readthedocs.io/en/latest/btrfs-man5.html)。

## 试验前保住源数据

- 保留密文、快照、回收站和文件系统元数据。不要运行 balance、defrag、discard/TRIM、repair、清理任务，也不要为了试验创建／删除快照；避免在受灾存储池安装套件或恢复业务写入。
- 恢复文件、日志、中间归档全部写到**源存储池之外的独立存储**。同一个池里的另一个目录或卷不够；预留密文副本、恢复输出和多份候选的空间。
- 普通文件级密文副本保留了加密后的字节，**没有保留**此路线需要的旧 extent、chunk tree 或快照历史。在易失证据保全后，条件允许时采用适当镜像或专业采集保留底层磁盘／文件系统。不要为了照抄通用教程而重启或拆除运行中的阵列。
- 只读文件描述符不会冻结可写挂载的文件系统。后台写入、访问时间、缓存和元数据事务仍可能影响一致性。不要换成底层磁盘路径来绕过已挂载设备拒绝、SSD 缓存层或 device-mapper；离线组装及禁止日志回放挂载需要单独审阅、兼容厂商的方案，Btrfs 仅有 `ro` 不一定阻止日志回放。

## 分阶段操作

1. **识别文件系统和存储层。** 记录挂载、文件系统 ID、子卷 ID、数据剖面、设备 ID、RAID/LVM/缓存、扇区大小、压缩、校验和算法及实际 inode 标志。单独检查现有快照，DSM 界面复选框不能代替这些信息。
2. **在副本上识别文件布局。** 用 `inspect_footer.py --input-copy COPY` 记录标记、模式、分段参数和范围。该工具只检查已分析的 EOF 布局，不预测 CoW 恢复。当前文件和快照分别盘点，列明硬链接和重复路径，避免扩大分母。
3. **审阅并固定外部工具版本。** 提权前阅读链接版本的兼容性说明和代码。其命令包括 `preflight`、`env`、`gens`、`survey`、`plan`、`csum`、`extract`。先对明确选定的一份文件做经过审阅的预检，不自动遍历全卷；保存完整结构化结果和 stderr。
4. **导出前核对映射。** 必须确认文件系统与设备关系正确，按 extent 映射读出的块与当前文件对应范围逐字节相同。覆盖相关剖面和设备，一份样本不能代表整个阵列。跨共享、跨会话检查新旧 extent 代数，不能猜一个时间阈值；边界检查、校验和自测及已知原件都应支持重组计划。
5. **小批导出、验收，再扩大。** 在独立存储的新位置导出少量文件，保存 extent 计划，把结果分为旧 extent 映射、位置推测、部分恢复或不可取得。完整原件对照及格式／应用检查通过后再扩大范围。失败候选和收据单列，不能为了续传把失败项标为完成。

## 已审阅外部版本的实际限制

以下来自本次对[固定版本源码](https://github.com/crt106/c3rb3r-btrfs-recovery/blob/b831f3a0f718677b889f2998ff09a0b925baa56b/skills/c3rb3r-btrfs-recovery/scripts/c3r_btrfs.py)的阅读（`parse_footer`、`formula_ranges`、`Volume`、`plan_file`、`cmd_preflight`），属于我们的接入审阅结论，不是作者已修复或我们已实盘验证的声明，也不是关闭保护的建议：

- `preflight` 可能输出 `FAIL` 后正常返回；无合适 extent 时某些映射检查会被跳过。不能只看退出码 0 或最后汇总，必须确认所需检查**存在且通过**。
- 可选的 `btrfs-map-logical` 对照会创建／删除一个可预测的 `/tmp` 文件。在已受侵主机上以 root 运行前应审阅此处，改用私有目录内独占创建的临时文件并核对临时挂载；不能称为完全不写文件的采集工具。
- 固定版本的尾部解析器主要检查长度，严格程度低于本仓库；公式函数只覆盖 `0x25` 参数 **10**。公式未知或结构可读都不能证明加密模式、改写范围或候选有效，也不能把不支持的模式当成不可恢复。
- 原生条带剖面、压缩和 inline extent 不在其常规重组覆盖范围。不能假定所有 DSM SHR 都只呈现一个 Btrfs 设备，也不能以“选择 stripe 0”证明设备选对了。
- 代数阈值错误、重复加密、去重、不完整元数据及现场持续变化都可能破坏重组。工具的 `exact` 只是映射分类，不等于独立的历史原件摘要。
- 校验和相同说明读取字节与所选校验和记录一致，不能独立证明推测映射属于哪个历史文件／版本。没有校验和不是通过，`self_ok = 0` 也不是自检成功；没有证据时，不得把解码错误归为原件固有损坏。

## 准确描述验证结果

| 结果 | 可以作出的结论 |
|---|---|
| 与独立同版本原件完整 SHA-256／逐字节一致 | 该文件精确恢复 |
| 映射经过验证，相关块校验和通过 | 映射和已检查块的完整性；列明未检查范围及历史假设 |
| 完整归档检查、解码或应用恢复通过 | 通过该格式／应用测试，不一定与历史原件完全相同 |
| 图片像素相同 | 像素级等价，元数据或编码字节仍可能不同 |
| 文件头能打开、预览正常或写出推测范围 | 仅为候选，不能宣布完整恢复 |

最终清单逐文件保留验证等级、部分恢复字节、不支持项和失败项。没有找到密钥应促使评估其他路线，而不是删除唯一的密文。
